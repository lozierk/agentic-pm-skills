This report attacks the wargame, not the PRD prose. Cycle 1 product/architecture decisions are treated as settled. Findings focus on where the wargame's move plan would mislead, under-specify, or fail to constrain the named executor.

## Findings

**M2.1 / M2.2 — Attack class 1 — The wargame orders food-ratings import completion before the reviewed `food_attributes` gate can succeed. Rev 4 requires every imported `food_name` to have a reviewed `food_attributes` record before a food-ratings import can become `complete`; M2.1's expected observation is "Kurt import: 370 rows; Cyndi: 371" as a completed import, while M2.2 performs the attribute seed and human review afterward. A literal executor either violates the promotion gate or gets blocked in M2.1 with no wargamed recovery. — Severity: BLOCKER — Suggested fix: Split M2.1 into parse/stage/failed-current-safety work and a later "promote to complete" step after M2.2 approval artifacts exist, or reorder the seed/review before final import promotion. Add an explicit test that an import with one missing reviewed attribute record remains non-current.**

**M3.1 / M3.2 / M4.2 / M4.4 / M5.2 / M6.3 — Attack class 1 — Rev 4 diner sets are not wargamed as a cross-cutting invariant. The wargame mostly reasons over "both profiles" and only tests N=1 household degeneracy, but rev 4 requires every request to carry a non-empty subset of household profiles, default everyone, with scoring, hard gates, substitutions, save gate, generation metadata, and library read behavior all respecting that set. A solo Cyndi meal containing Kurt Avoid food must be valid in the solo flow yet blocked when recomputed for everyone; the current move plan would likely over-block solo meals or under-test full-household recomputation. — Severity: BLOCKER — Suggested fix: Add a diner-set matrix to scorer, substitution, generation, save, and UI moves: everyone, Kurt-only, Cyndi-only, empty set rejected, outsider profile rejected, draft tampering rejected, solo-save/full-household-library recompute verified.**

**M4.0 / M4.1 / M4.2 / M4.3 — Attack class 1 — `llm_configs` is a rev 4 load-bearing addition, but the wargame has no move for seeding, resolving, validating, or version-echoing it. Generation moves assume Anthropic/model/effort as implementation constants, while the PRD requires every generation call to resolve the household's `llm_configs` row before any LLM call and to keep `credentials_ref` as a reference, never a secret. This creates a likely hardcoding path exactly where rev 4 introduced indirection. — Severity: DEGRADED — Suggested fix: Add a pre-generation move that seeds `llm_configs`, validates `vendor/model/per-stage effort/credentials_ref`, rejects missing or invalid config before LLM usage, resolves `platform-env` server-side only, and records the llm-config version in recipe metadata.**

**M4.2 / M4.4 / Ledger L6 — Attack class 1 — The lazy alias workflow is missing from the generation moves, and M4.2's second-order counter-move drifts toward a prebuilt alias table. Rev 4 says `food_aliases` are household-scoped, populated lazily from real match misses with recipe-context evidence, LLM-proposed, human-approved, and never pre-generated. Without a wargamed miss-logging and approval path, failed matches stay noisy forever or the executor invents a global/prebuilt alias shortcut. — Severity: DEGRADED — Suggested fix: Add an alias-flow move after verifier implementation: log unmatched proposed names with recipe context, propose candidate alias mappings offline, require household approval, enforce alias uniqueness/no-shadowing, and add regression tests for ambiguous aliases staying Unrated.**

**M4.2 / M6.2 — Attack class 1 — The wargame assumes progressive Stage-1 streaming and schema-validated idea cards can coexist without specifying the response framing. A single structured JSON response is easy to validate but may not allow the first complete card to render before the full object arrives; token streaming a partial JSON array does not automatically yield valid per-card UI objects. The counter-move "stream cards progressively" may not recover the latency target unless the API contract is shaped for progressive validation. — Severity: DEGRADED — Suggested fix: Define Stage-1 output as per-card framed events, NDJSON, SSE chunks, or another independently valid card envelope; validate each card independently, score it as soon as its key ingredients verify, and test first-card and all-cards latency separately.**

**M2.3 / M2.4 / M0.3 — Attack class 1 — The wargame protects final Supabase Storage objects but does not protect local extraction byproducts from CSV/PDF processing. Recon says Results PDFs contain DOB/client IDs; `pdftotext`, rendered PDF images, manual-entry scratch files, and review artifacts can easily land in the repo or in unignored temp paths during import work. This is a real PII leak path before Storage/RLS ever exists. — Severity: DEGRADED — Suggested fix: Add a "local data hygiene" move before import work: ignored private data/output directories, no extracted PDF text or rendered pages in git, secret/PII scan before commit, and explicit cleanup of scratch artifacts after imports.**

**M1.1 — Attack class 1 — Toolchain and dependency drift are under-wargamed. `create-next-app`, Next.js App Router defaults, Node versions, package-manager lockfiles, Supabase CLI, and Vercel build settings are all moving parts; the wargame treats scaffold as one stable command and jumps to env/bundle checks. A stale Node/npm/pnpm combo or shifted template default can consume the first build session and contaminate later debugging. — Severity: MINOR — Suggested fix: Pin Node version, package manager, create-next-app invocation flags, lockfile, Supabase CLI install path, and Vercel project settings in the first foundation move; record versions in the repo before feature work.**

**M6.2 — Attack class 1 — The latency verification move does not define sample size, cold/warm separation, or what counts as p50/p95. A few manual generations can make the p95 claim meaningless, especially with cold starts, prompt-cache first misses, and household data query variance. — Severity: MINOR — Suggested fix: Require a timed script with enough runs to compute useful p50/p95, separate cold-start and warm-cache samples, record first-card vs all-cards timings, and run against deployed Vercel with server-timing logs.**

**M3.1 — Attack class 2 — The wargame's "most likely failure" for scoring is empty-set math, but after rev 4 the more likely systemic failure is diner-set propagation drift. Empty-set bugs are easy to table-test inside `score_recipe`; diner sets cross API signatures, draft metadata, save gates, substitution verification, prompt steering, and library recomputation. That is where an executor is more likely to miss one path. — Severity: DEGRADED — Suggested fix: Reframe M3/M4/M5 scorer risk around diner-set propagation, with empty-set handling kept as one matrix row rather than the main expected failure.**

**M2.2 — Attack class 2 — The wargame over-trusts two-pass disagreement rate as the signal for attribute quality. Two LLM passes using the same underlying family can agree on the same wrong allergy/attribute omission, especially for hidden ingredients, culturally variable foods, oils, sauces, or edge cases like coconut/tree-nut semantics. Low disagreement is not the same as high recall for safety-relevant attributes. — Severity: DEGRADED — Suggested fix: Keep the two-pass diff, but add deterministic adversarial audits: per-attribute keyword probes, sentinel foods, block-list review for every safety-relevant positive, and a false-negative hunt for foods whose names imply an attribute but both passes marked empty.**

**M4.2 — Attack class 2 — The wargame treats exact-string miss rate as the main Stage-1 quality failure, but plausible composite ingredients are likely to be just as damaging. Recipe models naturally emit "vegetable stock", "curry paste", "gluten-free tamari", "mixed greens", and other food-prep concepts that may not map to Viome vocabulary items. Exact-string/canonicalization work does not solve recipe-ontology mismatch, so provisional scores can be based on too few meaningful ingredients while looking precise. — Severity: DEGRADED — Suggested fix: Add smoke prompts that force composites and prepared ingredients; require provisional score display to surface coverage prominently and downgrade confidence when key ingredients are unmatched or composite.**

**M6.2 — Attack class 2 — The wargame names region mismatch and sequential queries as the most likely production latency failure, but first-call cache misses and progressive-render framing are at least as likely to dominate perceived Stage-1 latency. The first request after a prefix change is a designed miss; if that miss regularly exceeds the all-cards p95 target, cache-hit smoke tests will not prove user experience. — Severity: MINOR — Suggested fix: Measure three latency classes separately: first call after prefix change, immediate cache-hit call, and cold Vercel function call. Decide which class the PRD's p50/p95 success signal applies to and report all three.**

**M1.4 — Attack class 3 — The route-enumeration counter-move is too narrow for a Next.js App Router build. "Enumerate all API routes and assert 401" can miss server actions, route handlers outside the expected tree, React Server Component data loaders, middleware-adjacent code, and any future direct import of the Anthropic client from a server component. A later feature can bypass `withAuth` without creating a new API route. — Severity: BLOCKER — Suggested fix: Make the service layer the only place that imports Anthropic, service-role Supabase, or household data readers; add static import bans, grep checks, and tests for every exported service function, not just HTTP routes. Include server actions in the unauthenticated/non-member abuse script.**

**M2.2 — Attack class 3 — The rubber-stamp counter-move assumes the executor can observe real human attention. "Review completed in one sitting at 400 rows/hour" is a useful smell, but the executor may only see approved repo files and cannot reliably know whether Kurt inspected them carefully. The wargame's forcing function helps, but it is not a verification mechanism. — Severity: DEGRADED — Suggested fix: Add review evidence that survives outside the human's head: per-batch notes, required corrections or confirmations on sentinel rows, a random backcheck batch after approval, and an explicit "no approval without at least one challenged item or double-check note" rule.**

**M2.4 — Attack class 3 — "Storage policies mirror table RLS" is not enough to prove signed URL safety. If the server uses a service-role client to sign object paths, the policy that matters is the server route's ownership check and path construction, not just `storage.objects` RLS. A non-member test can pass while a path-confusion or import-id spoofing bug still signs another household/profile's file. — Severity: DEGRADED — Suggested fix: Generate Storage object paths server-side from owned import rows only; never accept raw object paths from clients; test sibling household/profile/import IDs, path traversal strings, and signed-URL attempts through the service route.**

**M3.3 — Attack class 3 — The UI-constant counter-move is partially weak. Grepping for "Great/Good/Fair/Poor" catches label duplication, but it does not catch duplicated thresholds, duplicated point maps, or client-side recomputation that happens to use the same labels from config. — Severity: MINOR — Suggested fix: Add tests that mutate thresholds, point values, and labels independently in `scoring_configs`; assert the server payload and rendered UI follow without client code changes.**

**M0.2 — Attack class 4 — Several fork triggers depend on observations the executor may not actually have. Anthropic billing state, Vercel project creatability, Google OAuth settings, and Supabase dashboard auth logs are owner-account surfaces; Fable in Claude Code may not be logged in or authorized to see them. The wargame tells the executor to verify dashboard state without separating owner attestation from executable probes. — Severity: DEGRADED — Suggested fix: Split M0.2 into owner-provided artifacts and executor-run probes: owner supplies project refs, env var names, OAuth callback values, and screenshots or CLI outputs; executor verifies only via app-visible behavior and documented CLI/API calls available in the build environment.**

**M0.1 / Abort A3 / Abort A6 — Attack class 4 — The wargame still contains pre-markup and unresolved-ledger triggers that are retired by the governing inputs. Rev 4 and the ledger settle the stack, scoring defaults, topology, and dev strategy; a literal executor reading the wargame could wait on a closed markup gate or stop on A3/A6 despite the red-team contract saying rev 4 governs. — Severity: MINOR — Suggested fix: Patch the wargame header and Phase 0: mark M0.1 as completed by rev 4, replace "hold for markup" with "load rev4 deltas into battle plan", and explicitly retire A3/A6 in the active move list.**

**M2.2 — Attack class 4 — The failure signal "review completed in one sitting at 400 rows/hour" is ambiguous and not reliably observable. A fast expert review of a well-designed block-list artifact and a rubber-stamp can look identical from the executor's side if the only output is an approval file. — Severity: MINOR — Suggested fix: Treat review speed as a soft smell only; make the trigger observable through artifact quality: missing notes, no challenged rows, skipped sentinel checks, or no per-batch approval metadata.**

**Abort conditions — Attack class 5 — There is no hard stop for never obtaining a real Anthropic-capable production generation path. M0.2 allows LLM-free workstreams to proceed with mocks if the key is blocked or delayed, but no later abort says "stop if real Stage 1/Stage 2 calls cannot run before verification." This can carry a mocked app all the way into UI polish while the core product remains unproven. — Severity: DEGRADED — Suggested fix: Add an abort or phase gate before M4 completion: no generation feature may be called done until a real authenticated Anthropic call succeeds through resolved `llm_configs`, with usage recorded and zero unauthenticated usage.**

**Abort conditions — Attack class 5 — A4 is too loose as written. "Any mid-build scenario where two settled rules conflict" could stop the whole build for recoverable UI semantics, especially around "flagged but not cookable" cards where careful labeling can satisfy both clauses. That gives the executor an excuse to bounce manageable product-copy/state-machine work back to Kurt. — Severity: MINOR — Suggested fix: Narrow A4 to contradictions that cannot be resolved while preserving both safety invariants. For UI-state ambiguities, require a small state table and owner confirmation only if two compliant renderings have materially different product meaning.**

**Abort conditions — Attack class 5 — Missing abort for unexecutable security verification. The wargame makes §6.5 acceptance the final gate, but does not say to stop if the team cannot create/use the permanent disabled non-member test user, cannot obtain real session JWTs, or cannot run the script against anon-key paths. Skipping or hand-waving that script is exactly the known executor failure mode. — Severity: DEGRADED — Suggested fix: Add an abort: if the non-member acceptance script cannot be run end-to-end with real session JWTs and anon-key/service-route paths, do not call the build done. Report the blocker and the exact missing account/tooling state.**

**M5.1 — Attack class 6 — The wargame promotes Impeccable to a required move even though rev 4 says design-phase tooling is noted separately and intentionally absent from the PRD, and the red-team contract does not include it as a settled dependency. This is an invented external tool/access assumption inside the build battle plan. If `npx impeccable install` is unavailable, late, or convention-conflicting, the wargame creates failure unrelated to v1 safety. — Severity: DEGRADED — Suggested fix: Recast M5.1 as optional design tooling: use it if installed and compatible, otherwise proceed with the app's established frontend stack. Do not make it a build-readiness gate.**

**M4.1 — Attack class 6 — The wargame bakes provider-specific cache details not present in the PRD/ledger, including a 5-minute TTL assumption and exact usage-field behavior. Anthropic prompt caching is a settled design requirement, but the TTL and telemetry names are external-system behavior and may drift. — Severity: MINOR — Suggested fix: Keep the live two-call cache smoke test, but phrase the battle plan around observed cache-read evidence from the current SDK/API rather than a hardcoded TTL or field name.**

**M0.2 / M1.3 — Attack class 6 — The wargame's temporary magic-link/signups fallback can leak beyond "dev unblock" into product behavior without a ledger decision. The PRD allows additional sign-in methods later, but v1's settled user-facing path is invite-only Google OAuth. Leaving magic links enabled after debugging would silently widen the auth surface. — Severity: MINOR — Suggested fix: If temporary auth methods are used, require a cleanup test that only the intended v1 provider remains enabled in production, and record any permanent auth-method change as an owner decision rather than an executor convenience.**

**Cross-cutting counter-moves — Attack class 7 — Too many safeguards are phrased as executor discipline rather than executable guardrails. "Non-negotiable", "red-line", "never quietly", and "done reporting must quote output" are useful intent, but the named executor is the same class of model that the wargame says skips awkward gates, normalizes strings, uses service-role convenience, and declares done early. The wargame attacks this in prose but does not consistently make the bad path mechanically hard. — Severity: DEGRADED — Suggested fix: Convert each safety claim into an early checked-in script or CI target: importer quirk tests, RLS/storage/non-member script, unauthenticated route/service-action sweep, diner-set score matrix, fail-closed mutation test, secret scan, and latency harness. Require final build handoff to include command outputs from these scripts.**

**M1.2 / M3.2 — Attack class 7 — The wargame underestimates the executor mismatch in SQL/RLS and fail-closed logic. These are domains where LLM-generated code often looks plausible while being wrong in rare paths: service-role bypass, `security definer` search-path mistakes, optional chaining that fails open, policy tests run with the wrong key, or mutations not covered by fixtures. The wargame names the risks but still relies on the same executor to notice subtle security semantics. — Severity: DEGRADED — Suggested fix: Add adversarial verification beyond happy-path tests: run RLS tests only with anon/session clients, add negative tests per table and storage path, mutation-test the fail-closed branch, and require manual inspection of any `security definer` SQL with explicit `search_path` handling.**

**M4.2 / M4.4 / Ledger L6 — Attack class 7 — The wargame relies on the executor/model to preserve the alias-vs-substitution boundary under pressure. That boundary is semantically subtle: "scallions" may be the same food as "Green Onion (greens only)", while "onion powder" or "shallot" is not; "coriander" is regional; sauces and prepared foods can contain hidden attributes. A Fable-class executor may accept a plausible alias because it makes matching rates look better. — Severity: DEGRADED — Suggested fix: Make alias approval human-facing with explicit criteria and evidence, keep ambiguous cases unmatched, add examples of allowed and forbidden alias mappings to tests, and report unverified-match rate without treating it as a target to optimize at the expense of safety.**

**M6.1 — Attack class 7 — The final acceptance-test move still allows an executor-shaped escape hatch: passing "the stranger cannot sign in" can be mistaken for passing "an authenticated non-member cannot act." The wargame warns against narrowing the test, but the actual move should make the wrong test impossible to confuse with the right one. — Severity: DEGRADED — Suggested fix: The checked-in script should create or enable the disabled user, authenticate it, print the user id, prove there is no `household_members` row, run the four abuse checks, assert zero Anthropic usage, and disable the user. The final report must include those exact outputs.**

## Overall Verdict

**REWORK** — The PRD does not need to be rebuilt from these findings, but the wargame must be amended before it is a reliable execution battle plan. Required re-wargame areas:

1. M2 import order around reviewed `food_attributes` promotion.
2. Diner-set propagation across scoring, generation, substitution, saving, library display, and UI state.
3. `llm_configs` resolution and metadata as a first-class generation precondition.
4. Lazy per-household alias workflow from match misses.
5. Next.js auth wrapper coverage beyond API-route enumeration.
6. Stage-1 progressive streaming response framing and measurable latency harness.
7. Mechanical verification gates for the named executor's known blind spots.

Once those moves are revised, the plan can proceed to integration without reopening settled product decisions.
